---
name: governance-daily-report
description: Generate and deliver the configured personal Codex Desktop daily usage report in an authorized scheduled project chat. Uses private configuration and delivery receipts.
---

Hard runtime boundary: follow repository `AGENTS.md`. Use only Codex records/status as governance evidence. Never revisit logged external targets or query external services for enrichment or delivery verification. Only the configured email report/attachment and triggered Slack DM sends are allowed external runtime traffic; use immediate send responses and local ledger receipts. Missing recipient verification or uncertain outcomes require user action. Do not install packages or run external validation during checks.


Work from the repository root. Read `private/pilot.local.json`, `private/collector.local.json`, and `docs/collector.md`. Stop without sending if delivery_enabled is false. No real data goes into versioned files. Do not install dependencies or modify source during a scheduled run.

Use Python 3.11+ and the repository operating-system timezone adapter. No third-party packages or PYTHONPATH are needed. Display all notification times explicitly as ET; retain UTC in private machine-readable observations. Respect sandbox permissions; record a failure if execution cannot proceed. Do not silently change permissions or invent usage. Configuration account identity, recipient, and scheduled authorization must exist.

1. Determine today's date and current time in Eastern Time (ET). Do not send before 06:00. If delayed, label the actual cutoff and delay. Generate only today's report; do not flood the recipient with backfilled missed days.
2. Run `scripts/collect_usage.py --config private/collector.local.json --output private/usage-snapshot.json`, then `scripts/render_review.py --input private/usage-snapshot.json --output-dir private/reports/YYYY-MM-DD` using today's configured-zone date. The default reporting interval is the rolling seven days (168 hours) ending at the actual cutoff, including token activity and requested external sources/destinations; do not reset it at the calendar-week boundary. Use fixed dated paths so later reports do not overwrite previously linked details. Review diagnostics and surface gaps; never imply account-wide coverage. Preserve the generated summary's maximum three findings and its separate payload sources/destinations section. Keep the request-message metric, reporting interval and attribution limitations intact; do not describe these proxies as verified transfers or expand them with raw filenames, URLs or message contents.
3. If daily_report.email_enabled is explicitly false or no email recipient is configured, skip email and its ledger claim, and return the local report in chat. Otherwise discover the Outlook Email send tool. Send the concise plain-text summary only to daily_report.email in private configuration, with subject `PAIGe - Daily usage review - YYYY-MM-DD`. No CC/BCC. Attach only the HTML generated in this run at `private/reports/YYYY-MM-DD/daily-review.html`, using its resolved absolute local path in the Outlook send tool's `attachment_files` argument (not base64). Before claiming delivery, verify the file exists, is nonempty, and is smaller than the connector's 3 MB limit. If the attachment is missing, oversized, or unsupported, report the blocked email step in chat; do not silently send without it or substitute an older report. Tell the recipient the attached HTML report can be downloaded and opened in a browser; retain the local link in the project chat, not in email. Do not include prompt excerpts or attach configuration, raw logs, or other private files.
4. Before sending, claim the key `daily-email|YYYY-MM-DD|RECIPIENT` with `scripts/delivery_ledger.py claim --key ...`. Send only when send_allowed is true. Use safely quoted arguments; do not print configuration. Immediately after tool-confirmed success, call `complete` with the same key and a receipt recording the successful send response and attachment filename and byte size. Do not mark attachment delivery successful if the tool reports an attachment failure. If sending fails or its outcome is ambiguous, leave pending and report the failure; do not retry blindly. Existing sent/pending claims prevent duplicate sends.
5. Return the concise report in this scheduled run's chat with an absolute local HTML link, coverage, and email send outcome. The automation already creates this chat; do not create another. Reference this skill when reporting connector sends. Do not assert inbox receipt.

No model analysis of raw logs is necessary. Use deterministic scripts, do not read other chats or search external sources for coaching. Unknown processing and unset budget remain unavailable. Failures should identify the blocked step without exposing private data outside the configured channels.
