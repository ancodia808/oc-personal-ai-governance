# Team setup and maintenance

The README is the user-facing quick start. This document is the agent's detailed handoff after the onboarding interview. Reuse the user's settled answers; do not repeat the interview or copy another user's private settings. No credentials or real usage belong in shared files.

## Activate an approved configuration

1. Read the user's `private/onboarding.local.json` and `private/readiness.local.json`. Establish ownership before reading existing recipients in a reused checkout. Use the configured Python 3.11+ interpreter (`python3` where appropriate). Assume normal laptop/Git configuration unless an operation fails; investigate concrete failures rather than making users run routine diagnostics.
2. Prepare `private/pilot.local.json` from the approved onboarding settings, initially with `delivery_enabled: false`. Preserve unrelated existing fields during an authorized update. Prepare `private/collector.local.json` with `account_id` from verified local Desktop session metadata and `timezone: America/New_York`. Ask which account to use if multiple qualify; never read authentication tokens. Record the host timezone separately as `scheduler_host_timezone` in runtime settings and `host_timezone` in readiness. Check private destinations are ignored and untracked before writing personal data; perform these safeguards internally.
3. Generate a private collector snapshot and HTML/Markdown report using `docs/collector.md`. Review diagnostics and show the user a rendered local report link. No eligible logs means coverage is unresolved, not zero consumption. Keep report fixtures synthetic. Unsupported preferences must be resolved before activation: the current implementation uses daily 06:00 ET, Friday 18:00 ET and a 120-minute proxy threshold. The interval can be configured in the scheduler. Privacy requests that would require redacting project names need an implementation change before report delivery.
4. For selected channels, resolve the user's Slack workspace/ID and Outlook connection. Missing or declined channels stay disabled. Use the user's explicit test-send authorization to send one labelled test per opted-in channel, with separate durable test keys in the delivery ledger. Claim before sending and complete only after connector success; leave ambiguous sends pending. Do not bypass the disabled flag in a runtime skill: either send these setup tests directly under the user's authorization with no schedules active, or enable delivery only for an explicitly bounded test and restore it afterward. Store receipts privately. Wait for user confirmation of receipt before recurring activation. If no external channels were selected, skip this step and use project-chat delivery.
5. Discover the current project ID, available scheduling tools and suitable model from this user's environment. Create or update only this user's PAIGe schedules: daily report as a standalone local project job invoking `$governance-daily-report`; long-run and Friday checks as heartbeats in the current onboarding/monitoring chat invoking `$governance-monitor`. Do not create another monitoring chat unless requested. Prefix names with `PAIGe - `. Keep heartbeat instructions quiet on unchanged/non-actionable results. Reuse saved automation IDs; if names collide, inspect their project/target rather than replacing unrelated jobs.
6. Convert 06:00 daily and Friday 18:00 ET to the scheduler's supported timezone convention. Verify next-run times in Scheduled; do not copy the pilot's Central-time rules to another host. A fixed host-hour conversion is not sufficient if the host and Eastern DST rules diverge. Resolve that scheduling limitation before claiming year-round ET operation. Keep schedules paused while preparing them where supported; set delivery enabled and activate them only after the approved setup/test steps succeed. Save IDs, kind, target, timezone assumptions and readiness evidence privately. On a partial failure, pause newly activated PAIGe jobs and record what remains.
7. Have the user follow README Validation. Record per-step outcomes without inventing Mac or fresh-device test evidence. Provide the active schedule names, report link and any limitations. The delivery flag also gates chat-only runs; when channels are declined, enable the runtime flag but retain their individual channel flags as false.

## Update or migrate

Use `git status --short` and `git pull --ff-only`; preserve intentional local source changes instead of forcing reset/clean. Review changed skills and scripts. There are no third-party Python runtime packages to install. Retest affected behavior after interpreter, OS, account or connector changes. Keep the checkout path stable or update schedule project/target references after moving it.

On a new machine, clone shared source and repeat onboarding with the user's own identity. Do not automatically copy another user's configuration, logs or receipts. Reconcile old schedules before activating replacements to prevent two hosts sending duplicate reports. A local SQLite ledger does not deduplicate independently running machines.

## Disable, retain and remove

Pause the user's saved PAIGe schedules and set runtime `delivery_enabled` false. Both matter: pausing stops scheduled agent work; the flag prevents sends. Resume existing IDs after checking recipients and pending receipts rather than creating duplicates.

Agree a retention period and record it in private readiness. Retention is manual; no automatic purge is implemented. With schedules paused, review dated reports and observations against that period and ask for authorization to delete the concrete selected paths. Keep configuration and delivery receipts when resuming the same deployment. Deleting receipts can permit repeat sends. Do not remove source Codex session logs as part of PAIGe cleanup.

For removal, pause/delete the user's PAIGe schedules first, then delete only explicitly approved private artifacts or the named checkout. Validate absolute paths before any recursive operation. Slack/email copies, Codex chats and corporate backups have separate retention controls; deleting the checkout does not remove them.

## Packaging acceptance

The shared package includes interview and runtime skills, blank configuration/readiness contracts, synthetic examples, operating-system timezone support and reproducible tests. The Windows pilot demonstrates report generation, scheduled invocation, delivery and deduplication. Fresh-user laptop and macOS execution remain unobserved in the recorded evidence; do not infer them from README wording. Track those platform checks separately from completion of the packaging deliverables.
